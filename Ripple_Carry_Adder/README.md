# Parameterized Ripple-Carry Adder

This project implements a synthesizable, parameterized ripple-carry adder (RCA) in Verilog. It is part of the Arithmetic Datapath Library and is intended for RTL design, simulation, synthesis, and FPGA implementation practice.

## Function

The design adds two unsigned `N`-bit operands:

```text
a + b = sum, with carry propagation through all bit positions
```

The least-significant full adder starts with a constant carry-in of zero. Each following full adder receives the carry generated by the previous bit. The design exposes the carry from every bit rather than only the final carry-out.

For `N = 4`:

```text
a[3:0] + b[3:0]
       -> sum[3:0]
       -> carry[3:0]
```

`carry[i]` is the carry generated at bit `i`; therefore, `carry[N-1]` is the final carry-out.

## RTL implementation

The top-level module is `RCA` and has a configurable width:

```verilog
module RCA #(
    parameter N = 4
) (
    input  [N-1:0] a,
    input  [N-1:0] b,
    output [N-1:0] sum,
    output [N-1:0] carry
);
```

The implementation instantiates one `FA` full-adder module per bit using a generate loop. The full adder computes:

```text
s     = a_in ^ b_in ^ c_in
c_out = (a_in & b_in) | (c_in & (a_in ^ b_in))
```

The ripple-carry adder is a purely combinational circuit with no clock or reset. Each bit's carry output depends on the preceding bit's carry, creating a serial combinational carry-propagation path. As the adder width increases, this dependency can increase propagation delay. Clock-based setup and hold analysis is not applicable to this standalone design.

## Verification

`Testbench_code/RCA_tb.sv` contains a self-checking SystemVerilog testbench. It:

- Instantiates the DUT with `N = 4`.
- Runs directed cases, including zero, overflow, all-ones operands, and alternating patterns.
- Exhaustively tests all `2^4 x 2^4 = 256` input combinations.
- Checks both `sum` and the complete per-bit `carry` vector.
- Reports `ALL 261 TESTS PASSED` when no mismatch is detected.

The `#5` delay in the checker allows the combinational logic to settle before comparing the outputs.

To run the testbench in Vivado, select `RCA_tb` as the simulation top and choose **Run Behavioral Simulation**. A successful default-width run prints:

```text
Starting RCA testbench, N=4
ALL 261 TESTS PASSED
```

If any comparison fails, the testbench calls `$fatal`, causing the simulator run to report a failure instead of silently completing.

## FPGA implementation

The Vivado project targets the Digilent Arty A7-100 board and the `xc7a100tcsg324-1` device.

The constraints in `Constraints/RCA_Con.xdc` use this board mapping:

| RCA signal | Board resource |
|---|---|
| `a[3:0]` | Four onboard switches |
| `b[3:0]` | Four push-buttons |
| `sum[3:0]` | Four onboard LEDs |
| `carry[3:0]` | First four pins of Pmod JA |

All external ports are constrained as `LVCMOS33`. Because the RCA is combinational and has no clock, clock-based setup/hold analysis is not applicable. Project results should focus on functional simulation, synthesis resource utilization, implementation DRC, and other relevant implementation results. Optional combinational path-delay measurements should document their measurement method and use appropriate constraints. Do not claim timing closure or a maximum operating frequency for this standalone design.

## Running the project in Vivado

1. Open `Vivado/Ripple_Carry_Adder.xpr`.
2. Confirm that `RCA` is the synthesis top and `RCA_tb` is the simulation top.
3. Confirm that `Constraints/RCA_Con.xdc` is enabled.
4. Run behavioral simulation.
5. Run synthesis and implementation.
6. Review utilization, implementation DRC, and other relevant implementation reports.
7. Generate the bitstream after all pin and constraint checks pass.

If Vivado reports a missing `RCA.dcp`, remove the stale checkpoint reference from the project and rerun synthesis. A design checkpoint is a generated Vivado artifact; it is not required as a source file for this RTL implementation.

## Design trade-off

The RCA has a small area cost and simple regular structure, but its worst-case delay grows approximately linearly with `N` because each carry depends on the previous bit. This makes it useful as a baseline for comparison with faster adders such as carry-lookahead and carry-save architectures.
